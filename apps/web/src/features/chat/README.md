# Chat persistence (Phase 2B) and Groq streaming (Phase 2C)

`server.ts` is the server-only persistence entry point. It supplies the existing database and a fresh Better Auth request session to `createChatService`. The factory is an internal offline-test seam, not an API accepting caller-supplied identity. Phase 2C adds one authenticated streaming route and a testable handler using Vercel AI SDK/Groq. No UI, client navigation, tools, retrieval or note writes are added. Response completion/failure callbacks remain internal server operations, never client-controlled assistant-content writes.

## Operations and contracts

All operations return `{ ok: true, data }` or a safe `{ ok: false, error: { code, message } }`. Session verification precedes strict Zod validation and SQL. Unknown fields (including `ownerId`, mutable scope, role/status and caller time) are rejected. Foreign/missing conversations, projects and turns share `NOT_FOUND`. Unexpected failures return `UNAVAILABLE` without logging/returning driver errors or content.

- `createConversation({ title, projectId? })`: null/omitted project means global. A project scope must be owned and is locked `FOR SHARE` during creation. Scope and owner have no update operation; there is no rename/delete operation. Titles are trimmed, 1–300 characters; a future caller may derive a title from the first message without an LLM call.
- `listConversations({ limit?, offset? })`: owned history, `updatedAt DESC, id DESC`.
- `getConversation({ conversationId, limit?, offset? })`: conversation, a bounded message page, and `pendingTurn: { turnId, abandoned } | null`, even if the pending message is outside the page. A read-only REPEATABLE READ transaction gives one coherent snapshot. Reading never repairs or changes history.
- `beginTurn({ conversationId, turnId, content, modelId? })`: atomically writes user/completed plus assistant/pending and advances conversation activity. User content is preserved exactly (nonblank, at most 100,000 characters). Model ID is optional/null or a nonblank string up to 200 characters; future provider code, not a client/model, chooses the supported ID.
- `completeResponse({ conversationId, turnId, content })`: pending to completed, with nonblank content up to 100,000 characters. Model ID comes from the persisted begin operation and is not replaced by callbacks.
- `failResponse` / `stopResponse({ conversationId, turnId, content? })`: pending to failed/stopped. Optional content can retain partial output, including empty output, but must never be a raw exception or secret. Omission preserves stored content. The user message stays completed and unchanged.
- `recoverAbandonedTurn({ conversationId, turnId })`: explicitly changes an expired pending assistant to failed, preserving its content. A nonexpired pending turn conflicts; already terminal turns are returned unchanged.
- `getGenerationContext({ conversationId, turnId })`: internal read-only REPEATABLE READ query. Returns authorized project name/description (or null) and at most eight recent completed user/assistant pairs from the owned conversation, excluding the current turn. Both roles must be completed and joined on conversation and turn IDs. The query bounds fetched text before prompt assembly (details below); it never reads notes.

Both list/page contracts default to 50 records, maximum 100, offset 0–100,000. Offset pagination is deterministic for a fixed snapshot, not a frozen history across requests while activity changes. Message order is `createdAt ASC, role DESC, id ASC`: user precedes assistant when a pair shares its timestamp. New turns use a PostgreSQL-clock timestamp strictly newer than the locked conversation activity timestamp. Failed/stopped messages remain in history; only completed pairs become provider context, subject to the bounded Phase 2C prompt policy below.

## Idempotency, concurrency and interruption

Every turn mutation takes an ownership-filtered `FOR UPDATE OF chat_conversations` lock in a short READ COMMITTED transaction. Subsequent statements see the previous lock holder's commit. Message queries/updates also include an owned-conversation predicate. Project-scoped access additionally requires the project still belongs to the session owner. There is no ownership-transfer feature.

`(conversation_id, turn_id, role)` is unique. A partial unique index on conversation ID where status is pending adds database-level protection against more than one pending assistant, even if a writer violates the service protocol. A CHECK allows pending only for assistants (user messages must be completed with no model ID). Raw SQL can still violate pairing or scope immutability: all application writers must use this service; no triggers or new auth/RLS behavior are introduced.

A begin replay requires the same exact user content and normalized model ID, returns both existing records with `replayed: true`, and never restarts generation or rewrites timestamps. Changed payloads conflict; an incomplete pair fails closed. Exact terminal callback replay is a no-op; changed terminal content/status conflicts. Once failed/stopped/completed, a turn cannot be resurrected. A new attempt needs a **new turn ID** and preserves the previous pair.

**Provider contract:** call a provider only after a confirmed successful begin with `replayed: false`, and only after the begin transaction commits. Never interpret replayed pending as permission to start another provider call. Hold no database transaction while waiting on the provider. On ambiguous begin/commit failure, inspect/replay the same turn ID rather than issuing a new one. An unknown successful commit may leave an unstarted pending record; use the interruption protocol, not an automatic duplicate generation.

The pending deadline is **10 minutes from the assistant's creation timestamp**, measured against PostgreSQL `clock_timestamp()` after acquiring the conversation lock. No client time, polling worker, heartbeat field or background job is used. This is an implementation policy for PM review, not a measured provider SLA. Phase 2C bounds provider calls to 120 seconds, below it; otherwise a new turn may begin while an obsolete external request is still running, though the old response can no longer be persisted.

A replay/read reports abandonment at the inclusive deadline without writing. Explicit recovery, or beginning a different turn, marks the abandoned pending record failed under the same conversation lock. Begin retires the old response and inserts the new pair atomically, so a failed insert cannot consume the recovery. Completion after the deadline conflicts; a late callback cannot overwrite a recovered/stopped response. Failed/stopped records are distinguishable from an outstanding pending record; there is no additional `interrupted` database status.

Conversation activity, response finalization, and any recovery/new pair commit together. No-op replays do not move history to the top. All writers use server-selected times; `$onUpdate` remains a Drizzle hook rather than a database trigger.

## Phase 2C endpoint and protocol

`POST /api/chat/stream` uses the Node runtime (`maxDuration = 180` seconds for compatible hosting platforms). It requires an existing conversation, Better Auth session cookies, `Content-Type: application/json`, and an `Origin` exactly matching the origin of configured `BETTER_AUTH_URL`. Missing/null/foreign origins and a supplied `Sec-Fetch-Site` other than `same-origin` are rejected. No CORS origin is reflected. Proxy/frontend configuration must preserve this same-origin boundary.

The strict request body contains **only** `{ conversationId, turnId, content }`. IDs must be UUIDs; content is nonblank, well-formed Unicode without NUL, preserved exactly and limited to 4,000 JavaScript string units. The streamed UTF-8 request body is capped at 32,768 bytes, independently of `Content-Length`. Owner, project/scope, model, assistant content, status and all other extra fields are rejected. The route authenticates first; the service independently derives ownership from a fresh session on each operation. A foreign/missing conversation returns 404 before inference. There is no public conversation-creation or terminal-write endpoint.

For a newly persisted turn, the response is **custom SSE**, not the AI SDK UI-message transport:

- `start`: `{ conversationId, turnId }` after confirmed begin/context preparation.
- `text-delta`: `{ text }`; this is provisional output, **not** confirmation of a save.
- `finish`: `{ turnId, status: "completed", persisted: true, messageId }`, emitted only after the complete response and conversation activity commit successfully.
- `error`: `{ code, message, persistence: "confirmed" | "unconfirmed", status? }`. Confirmed failed/stopped saves include that status. Unconfirmed persistence must trigger history inspection, not automatic regeneration.

Frames have `event: <name>\ndata: <JSON>\n\n` encoding, with JSON escaping for message newlines. Responses use `Cache-Control: no-store`; SSE also requests disabled proxy buffering. Once streaming starts the HTTP status is 200, so the client must inspect terminal events and treat EOF **without** a confirmed terminal event as ambiguous.

A successful begin with `replayed: true` instead returns JSON `{ ok: true, replayed: true, abandoned, user, assistant }` with persisted status/content, without context queries or provider calls. Pending (including abandoned), failed, stopped and completed replays never regenerate. A changed payload/model or competing active turn returns 409. Configuration/key absence is checked before begin and returns a safe 503 without creating a turn. An ambiguous begin returns a safe error with no inference or speculative terminal update; inspect/replay the same ID.

Pre-stream errors use `{ ok: false, error: { code, message } }`: 400 invalid input, 401 unauthenticated, 403 origin rejection, 404 inaccessible conversation, 409 conflict, 413 oversized body, 415 wrong media type, 503 unavailable/configuration/unconfirmed save. A request already aborted, or stopped before inference after confirmed begin, uses 499 if a response can still be delivered. No raw SDK/SQL exceptions, stack traces, provider bodies, credentials or private message content are included in errors or logs.

### Provider, prompt and cost bounds

- `ai@7.0.176`, `@ai-sdk/groq@4.0.85` (lockfile-resolved); both require **Node >=22**. Local checks use Bun 1.3.13 / Node 24.13.0. Groq is instantiated directly, never through AI Gateway, using fixed **`openai/gpt-oss-120b`**.
- `GROQ_API_KEY` is required, nonempty and server-only in `.env.schema`, inheriting sensitive-by-default handling. Generated Varlock types include it; no `NEXT_PUBLIC_` key or client prop is added. No environment override file needs to be inspected to implement/test this path.
- The bounded query selects eight latest completed pairs, each field's first 2,000 PostgreSQL characters, then restores chronological order. Prompt assembly retains the newest contiguous set fitting 6,000 JavaScript string units across both roles. It may omit older turns and truncate retained fields; stored history itself is untouched. Current persisted input is appended once, not duplicated from history.
- Global chats get **no project knowledge**. Scoped chats get only the owned project's name (first 200 PostgreSQL characters) and description (first 1,000), JSON-encoded as explicitly untrusted metadata, not instructions. No notes, other conversations, retrieval or tools are queried. Instructions explicitly prohibit claiming access to unavailable Solyn knowledge.
- Output is capped at **1,024 tokens** (including model reasoning as governed by Groq) and 20,000 JavaScript string units. Reasoning effort is `low`; `reasoningFormat: "parsed"` keeps reasoning separate. Unrepresentable text (NUL or malformed Unicode) fails safely before that delta is emitted or saved. Only answer text deltas are streamed/persisted; reasoning, sources, tool events, provider metadata and usage are not exposed or stored. There are no tools or automatic multi-step generations.
- Inference has `maxRetries: 0`; stream retries are omitted/disabled and `onError` never requests retry. The handler overrides the SDK's raw-error logging default. A 120-second abort deadline and abort-aware reader bound a stalled stream, even when a test provider ignores its abort signal. No database transaction spans provider work. Character bounds are conservative workload controls, **not an exact tokenizer or free-tier quota guarantee**; Groq rate limits remain authoritative.

### Failure, cancellation and persistence lifecycle

Only a confirmed **new** begin permits one provider invocation. Context/configuration/provider errors never authorize another inference. Provider auth/config errors, rate limits, timeouts, network errors, rejected requests, empty answers and output limits have fixed safe categories. Only a nonempty answer with provider finish reason `stop` is completed. A length-limited answer is failed/incomplete, retaining any already-visible partial output.

Provider failure/timeout saves `failed`; request abort or response-body cancellation aborts inference and saves `stopped` with safe accumulated answer text. There is one terminal write attempt, and final callbacks still enforce Phase 2B's immutable terminal states. A disconnect during completion persistence does not race a second stopped write against that commit. If completion/failure/stop persistence is not confirmed, no success is reported, no terminal overwrite is attempted, and no provider retry occurs. Reload/replay distinguishes a committed result with a lost acknowledgement from a still-pending turn. Old callbacks cannot overwrite a recovered/stopped turn.

Process termination or hosting/network behavior may prevent finalization entirely. Partial output is saved on terminal transitions, **not per chunk**; a process crash can leave a pending row with no partial output. The existing ten-minute explicit/new-turn recovery protocol remains the fallback; replay alone never repairs or starts work. Session expiry can also prevent terminal persistence rather than bypassing authorization. No worker, heartbeat or new status/schema is introduced.

## Verification boundary

`chat.test.ts` uses the real Drizzle SQL builder over scripted drivers, plus a deterministic in-memory transaction/lock simulator for simultaneous begins. It tests owner predicates, ordering, validation, transaction routing, replay, contention decisions, deadlines, and rollback/error paths **offline**. It does not prove actual PostgreSQL locks, constraints, MVCC snapshots, persistence, network failures, or rollback/concurrency behavior. `packages/db/src/chat-schema.test.ts` checks metadata, relational query compilation, and generated migration structure without connecting.

`stream-handler.test.ts` exercises the real SDK with `MockLanguageModelV4` and the real Groq adapter with a mocked fetch. Tests cover the origin/session/body boundary, ownership denial, bounded chronological prompts, no inference on replay/ambiguous begin, concurrent HTTP orchestration, streamed errors, private reasoning/error suppression, no retries, confirmed-save acknowledgements, timeout, disconnect, late disconnect during save and unconfirmed terminal writes. All tests are offline; none calls Groq or writes a database.

**The Phase 2B migration is not approved/applied.** This endpoint is implemented/buildable but is not a live persistence/provider integration verification. Do not test it against a real database/provider until PM authorizes the exact target and actions. Before database execution, review the migration and the `public` schema Data API exposure/grants/RLS gate in `packages/db/src/migrations/README.md`. Better Auth sessions are not Supabase Auth JWTs; do not use `auth.uid()` as Solyn's owner ID. Real PostgreSQL constraints/MVCC/concurrency, platform disconnect propagation and live Groq behavior remain unverified.

## Phase 2D boundary

Future UI work must create conversations through separately approved authenticated server entry points, retain one turn UUID across ambiguous submit retries, consume this SSE protocol (or explicitly approve a protocol change), distinguish provisional output from confirmed persistence, abort on stop/navigation, render failed/stopped/abandoned states and reload rather than regenerate after ambiguous completion. No chat UI, conversation navigation/title workflow, UI transport hook, quotas, retrieval, citations, tools or note writes are included here.
