# Ask Solyn — persistence, Groq streaming and confirmed AI note drafts

**Current status:** Phase 3, including the P3.4B sign-out warning fix, is merged into `main` through PR #1 (`0ca0856`). Phase 2/P3.2 audit sections below preserve historical evidence and plans, not current merge gates. Live PostgreSQL write/concurrency, Groq tool and authenticated browser verification remain distinct from offline tests; retrieval/citations are not implemented.

`server.ts` is the server-only persistence entry point. It supplies the existing database and a fresh Better Auth request session to `createChatService`. The factory is an internal offline-test seam, not an API accepting caller-supplied identity. Phase 2C adds one authenticated streaming route and a testable handler using Vercel AI SDK/Groq. Phase 2D adds the chat UI inside the existing workspace shell. P3.2 adds one schema-only `prepareNote` tool and a durable editable draft preview. P3.3 adds explicit user confirmation through the workspace service, with atomic note/receipt creation and idempotent replay; the model still has no note-writing capability or retrieval. Response completion/failure callbacks remain internal server operations, never client-controlled assistant-content writes.

## Operations and contracts

All operations return `{ ok: true, data }` or a safe `{ ok: false, error: { code, message } }`. Session verification precedes strict Zod validation and SQL. Unknown fields (including `ownerId`, mutable scope, role/status and caller time) are rejected. Foreign/missing conversations, projects and turns share `NOT_FOUND`. Unexpected failures return `UNAVAILABLE` without logging/returning driver errors or content.

- `createConversation({ title, projectId? })`: null/omitted project means global. A project scope must be owned and is locked `FOR SHARE` during creation. Scope and owner have no update operation; there is no rename/delete operation. Titles are trimmed, 1–300 characters; the UI derives a short title from the first submitted message without an LLM call.
- `listConversations({ limit?, offset? })`: owned history, `updatedAt DESC, id DESC`.
- `getConversation({ conversationId, limit?, offset?, latest? })`: conversation, a bounded message page, and `pendingTurn: { turnId, abandoned } | null`, even if the pending message is outside the page. A read-only REPEATABLE READ transaction gives one coherent snapshot, including a nullable owner-checked proposal on each completed assistant message. Proposal reads are bounded by the message page. Reading never repairs or changes history. `latest: true` reads in reverse order then returns each page chronologically; omitted/false preserves the original oldest-first behavior.
- `beginTurn({ conversationId, turnId, content, modelId? })`: atomically writes user/completed plus assistant/pending and advances conversation activity. User content is preserved exactly (nonblank, at most 100,000 characters). Model ID is optional/null or a nonblank string up to 200 characters; future provider code, not a client/model, chooses the supported ID.
- `completeResponse({ conversationId, turnId, content })`: pending to completed, with nonblank content up to 100,000 characters. Model ID comes from the persisted begin operation and is not replaced by callbacks.
- Internal `completeProposal({ conversationId, turnId, content, draft })`: fresh-session/owned-conversation lock, source user/assistant and project/date/deadline revalidation, then assistant completion + one original proposal insert + activity in one READ COMMITTED transaction. Exact replay returns the same proposal; changed payloads conflict. No note insertion or receipt mutation.
- `getNoteProposal({ proposalId })`: one authorized completed assistant source, original validated draft and scope/receipt DTO in a read-only REPEATABLE READ snapshot. Foreign/missing proposals are indistinguishable. No repairs or writes.
- `failResponse` / `stopResponse({ conversationId, turnId, content? })`: pending to failed/stopped. Optional content can retain partial output, including empty output, but must never be a raw exception or secret. Omission preserves stored content. The user message stays completed and unchanged.
- `recoverAbandonedTurn({ conversationId, turnId })`: explicitly changes an expired pending assistant to failed, preserving its content. A nonexpired pending turn conflicts; already terminal turns are returned unchanged.
- `getGenerationContext({ conversationId, turnId })`: internal read-only REPEATABLE READ query. Returns authorized project name/description (or null) and at most eight recent completed user/assistant pairs from the owned conversation, excluding the current turn. Both roles must be completed and joined on conversation and turn IDs. The query bounds fetched text before prompt assembly (details below); it never reads notes.

Both list/page contracts default to 50 records, maximum 100, offset 0–100,000. Offset pagination is deterministic for a fixed snapshot, not a frozen history across requests while activity changes. Message order is `createdAt ASC, role DESC, id ASC`: user precedes assistant when a pair shares its timestamp. New turns use a PostgreSQL-clock timestamp strictly newer than the locked conversation activity timestamp. Failed/stopped messages remain in history; only completed pairs become provider context, subject to the bounded Phase 2C prompt policy below.

## Idempotency, concurrency and interruption

Every turn mutation takes an ownership-filtered `FOR UPDATE OF chat_conversations` lock in a short READ COMMITTED transaction. Subsequent statements see the previous lock holder's commit. Message queries/updates also include an owned-conversation predicate. Project-scoped access additionally requires the project still belongs to the session owner. There is no ownership-transfer feature.

`(conversation_id, turn_id, role)` is unique. A partial unique index on conversation ID where status is pending adds database-level protection against more than one pending assistant, even if a writer violates the service protocol. A CHECK allows pending only for assistants (user messages must be completed with no model ID). Raw SQL can still violate pairing or scope immutability: all application writers must use this service; no triggers or new auth/RLS behavior are introduced.

A begin replay requires the same exact user content and normalized model ID, returns both existing records with `replayed: true`, and never restarts generation or rewrites timestamps. Changed payloads conflict; an incomplete pair fails closed. Exact terminal callback replay is a no-op; changed terminal content/status conflicts. Once failed/stopped/completed, a turn cannot be resurrected. A new attempt needs a **new turn ID** and preserves the previous pair.

**Provider contract:** call a provider only after a confirmed successful begin with `replayed: false`, and only after the begin transaction commits. Never interpret replayed pending as permission to start another provider call. Hold no database transaction while waiting on the provider. On ambiguous begin/commit failure, inspect/replay the same turn ID rather than issuing a new one. An unknown successful commit may leave an unstarted pending record; use the interruption protocol, not an automatic duplicate generation.

The pending deadline is **10 minutes from the assistant's creation timestamp**, measured against PostgreSQL `clock_timestamp()` after acquiring the conversation lock. No client time, polling worker, heartbeat field or background job is used. This is an implementation policy for PM review, not a measured provider SLA. Phase 2C bounds provider calls to 120 seconds, below it; otherwise a new turn may begin while an obsolete external request is still running, though the old response can no longer be persisted.

A replay/read reports abandonment at the inclusive deadline without writing. Explicit recovery, or beginning a different turn, marks the abandoned pending record failed under the same conversation lock. Begin retires the old response and inserts the new pair atomically, so a failed insert cannot consume the recovery. Completion after the deadline conflicts; a late callback cannot overwrite a recovered/stopped response. Failed/stopped records are distinguishable from an outstanding pending record; there is no additional `interrupted` database status.

Conversation activity, response finalization, and any recovery/new pair commit together. No-op replays do not move history to the top. All writers use server-selected times; `$onUpdate` remains a Drizzle hook rather than a database trigger.

## Phase 2C endpoint and protocol

`POST /api/chat/stream` uses the Node runtime (`maxDuration = 180` seconds for compatible hosting platforms). It requires an existing conversation, Better Auth session cookies, `Content-Type: application/json`, and an `Origin` exactly matching the origin of configured `BETTER_AUTH_URL`. Missing/null/foreign origins and a supplied `Sec-Fetch-Site` other than `same-origin` are rejected. No CORS origin is reflected. Proxy/frontend configuration must preserve this same-origin boundary.

The strict request body contains **only** `{ conversationId, turnId, content }`. IDs must be UUIDs; content is nonblank, well-formed Unicode without NUL, preserved exactly and limited to 4,000 JavaScript string units. The streamed UTF-8 request body is capped at 32,768 bytes, independently of `Content-Length`. Owner, project/scope, model, assistant content, status and all other extra fields are rejected. The route authenticates first; the service independently derives ownership from a fresh session on each operation. A foreign/missing conversation returns 404 before inference. Conversation creation is a separate authenticated Server Action; no terminal-write operation is exposed to clients.

For a newly persisted turn, the response is **custom SSE**, not the AI SDK UI-message transport:

- `start`: `{ conversationId, turnId }` after confirmed begin/context preparation.
- `text-delta`: `{ text }`; this is provisional output, **not** confirmation of a save.
- `finish`: `{ turnId, status: "completed", persisted: true, messageId, proposal: ProposalView | null }`, emitted only after assistant/activity and, if present, the original proposal commit successfully. This confirms chat/proposal persistence, **not a saved note**.
- `error`: `{ code, message, persistence: "confirmed" | "unconfirmed", status? }`. Confirmed failed/stopped saves include that status. Unconfirmed persistence must trigger history inspection, not automatic regeneration.

Frames have `event: <name>\ndata: <JSON>\n\n` encoding, with JSON escaping for message newlines. Responses use `Cache-Control: no-store`; SSE also requests disabled proxy buffering. Once streaming starts the HTTP status is 200, so the client must inspect terminal events and treat EOF **without** a confirmed terminal event as ambiguous.

A successful begin with `replayed: true` instead returns JSON `{ ok: true, replayed: true, abandoned, user, assistant, proposal: ProposalView | null }` with persisted status/content, without context queries or provider calls. Pending (including abandoned), failed, stopped and completed replays never regenerate. A changed payload/model or competing active turn returns 409. Configuration/key absence is checked before begin and returns a safe 503 without creating a turn. An ambiguous begin returns a safe error with no inference or speculative terminal update; inspect/replay the same ID.

Pre-stream errors use `{ ok: false, error: { code, message } }`: 400 invalid input, 401 unauthenticated, 403 origin rejection, 404 inaccessible conversation, 409 conflict, 413 oversized body, 415 wrong media type, 503 unavailable/configuration/unconfirmed save. A request already aborted, or stopped before inference after confirmed begin, uses 499 if a response can still be delivered. No raw SDK/SQL exceptions, stack traces, provider bodies, credentials or private message content are included in errors or logs.

### Provider, prompt and cost bounds

- `ai@7.0.176`, `@ai-sdk/groq@4.0.85` (lockfile-resolved); both require **Node >=22**. Local checks use Bun 1.3.13 / Node 24.13.0. Groq is instantiated directly, never through AI Gateway, using fixed **`openai/gpt-oss-120b`**.
- `GROQ_API_KEY` is required, nonempty and server-only in `.env.schema`, inheriting sensitive-by-default handling. Generated Varlock types include it; no `NEXT_PUBLIC_` key or client prop is added. No environment override file needs to be inspected to implement/test this path.
- The bounded query selects eight latest completed pairs, each field's first 2,000 PostgreSQL characters, then restores chronological order. Prompt assembly retains the newest contiguous set fitting 6,000 JavaScript string units across both roles. It may omit older turns and truncate retained fields; stored history itself is untouched. Current persisted input is appended once, not duplicated from history.
- Global chats get **no project knowledge**. Scoped chats get only the owned project's name (first 200 PostgreSQL characters) and description (first 1,000), JSON-encoded as explicitly untrusted metadata, not instructions. No notes, other conversations or retrieval are queried; the schema-only tool has no `execute` function. Instructions explicitly prohibit claiming access to unavailable Solyn knowledge.
- Output is capped at **1,024 tokens** (including model reasoning as governed by Groq) and 20,000 JavaScript string units shared by visible text and serialized/streamed tool arguments; the tool-only notice also fits that budget. Reasoning effort is `low`. GPT-OSS rejects `reasoning_format`; it is omitted, with no unsupported `includeReasoning` substitute. Reasoning stays private. Unsafe text (NUL/lone surrogates) is rejected. Raw tool fragments/events, reasoning, sources, provider metadata and usage are never sent as previews or stored in chat text. Only one fully validated draft becomes a durable proposal; Groq parallel tool calls are disabled. There is no `execute`, automatic save or multi-step generation.
- Inference has `maxRetries: 0`; stream retries are omitted/disabled and `onError` never requests retry. The handler overrides the SDK's raw-error logging default. A 120-second abort deadline and abort-aware reader bound a stalled stream, even when a test provider ignores its abort signal. No database transaction spans provider work. Character bounds are conservative workload controls, **not an exact tokenizer or free-tier quota guarantee**; Groq rate limits remain authoritative.

### Failure, cancellation and persistence lifecycle

Only a confirmed **new** begin permits one provider invocation. Context/configuration/provider errors never authorize another inference. Provider auth/config errors, rate limits, timeouts, network errors, rejected requests, empty answers and output limits have fixed safe categories. Normal text requires a nonempty answer ending `stop`; one validated `prepareNote` call requires `tool-calls`. Tool-only success uses `Draft ready for review. No note has been saved.` Invalid/unknown/multiple calls, partial/malformed arguments, scope/date conflicts and budget overflow fail without an actionable draft. A length-limited answer is failed/incomplete, retaining only already-visible provisional text.

Provider failure/timeout saves `failed`; request abort or response-body cancellation aborts inference and saves `stopped` with safe accumulated answer text. There is one terminal write attempt, and final callbacks still enforce Phase 2B's immutable terminal states. A disconnect during completion persistence does not race a second stopped write against that commit. If completion/failure/stop persistence is not confirmed, no success is reported, no terminal overwrite is attempted, and no provider retry occurs. Reload/replay distinguishes a committed result with a lost acknowledgement from a still-pending turn. Old callbacks cannot overwrite a recovered/stopped turn.

Process termination or hosting/network behavior may prevent finalization entirely. Partial output is saved on terminal transitions, **not per chunk**; a process crash can leave a pending row with no partial output. The existing ten-minute explicit/new-turn recovery protocol remains the fallback; replay alone never repairs or starts work. Session expiry can also prevent terminal persistence rather than bypassing authorization. No worker, heartbeat or new status/schema is introduced.

## Phase 2D UI and authenticated actions

- `/chat`: new **General chat**. `/chat?projectId=<uuid>`: new authorized project chat, reached from Project Detail. `/chat?conversationId=<uuid>`: an existing owned conversation. Query IDs are validated and conflicting scopes rejected. The project name is resolved through the existing authenticated workspace service, never from query-supplied metadata. Scope is immutable; the visible project label links back to its project. Sidebar Ask Solyn always opens general scope; header New chat retains a known project scope.
- `actions.ts` exports `createConversation`, `listConversations`, `getConversation`, `getNoteProposal` and `listProposalProjects`. They call the existing fresh-session/ownership-checked chat/workspace services. Project choices return only owned IDs/names, using bounded pagination; names never resolve identity. No client-callable begin, assistant completion/failure/stop, proposal finalization or recovery write action is introduced.
- Opening New chat performs no mutation. The first valid submit creates a conversation with the first 80 Unicode code points of whitespace-normalized message text as its title, then sends the original content. Confirmed creation is retained and navigation to its conversation URL is requested before streaming; a send failure cannot create another conversation automatically. A lost creation acknowledgement blocks recreation and directs the user to history; creation itself has no new idempotency schema/API.
- The sidebar shows at most five recent conversations, only when present. Its query fails safely if chat tables are unavailable, without preventing project/note pages from rendering. The History menu pages 20 owned conversations at a time and supports keyboard access/Escape. Scoped rows say Project chat; opening one resolves and displays the authorized project name.
- Existing conversations open the latest 50 messages. Load older pages backwards in batches of 50, retaining at most 500 rendered messages while allowing further older pages. Reload saved history returns to the latest page before continuing a conversation. Offset pages are not a frozen snapshot across concurrent activity. New messages and provisional text never become provider context from the browser; context stays server-selected.
- `ChatSession` owns one in-flight request, one unresolved turn ID and exact submitted content. `transport.ts` incrementally decodes UTF-8 and SSE lines/frames across arbitrary chunk boundaries, including CR/LF/CRLF and multiline data. JSON replays are identity/status checked and never imply regeneration. Unknown private error messages are not displayed. Text remains provisional until a matching persisted finish, a validated terminal replay, or an actual completed history read confirms persistence.
- EOF, malformed responses, network failure, unconfirmed writes and Stop trigger a persisted-history read. If the read also fails, new turns and retries are blocked until a successful read. If no saved turn is observed, **Retry same message** is explicit and retains its original turn ID/content; it does not create a new conversation or UUID. Live pending replays block inference. Abandoned pending is shown as interrupted; only an explicit new message retires it through the existing begin protocol. No recovery write happens on a read or replay.
- Stop aborts `fetch`; navigation aborts the visible request too. A still-pending snapshot after Stop is not mislabeled stopped: provisional partial text is retained, and Reload saved history checks finalization. Creation cannot be canceled mid-Server-Action, but a confirmed result after Stop is retained without starting inference. A result arriving after leaving the view does not navigate the user back.
- Up to ten view-local chat sessions retain unsent drafts and unresolved attempts while moving between chat query routes. Returning to a cached conversation adopts the newly authorized server snapshot without discarding its draft; an older route response never replaces an active/promoted stream. Promotion of a newly created chat keeps the same active session, so URL updates do not abort its stream. There is no local/session storage or module-global user cache. Leaving chat/reloading the document can discard these unsent drafts/attempt IDs; returning reads persisted state rather than automatically sending. The workspace shell is keyed by authenticated account to reset client state on account changes.
- Desktop chat uses the same fixed canvas with only the message region scrolling; header/composer stay in place. Mobile keeps normal document scrolling and the existing navigation drawer, with a sticky bottom composer. Auto-scroll follows output only while already near the bottom. Enter sends, Shift+Enter inserts a newline, IME composition does not submit, and the composer enforces the shared 4,000-unit input contract. Future text typed while sending is preserved.
- Formatting is deliberately small: escaped text, headings, lists, inline code and fenced code blocks. No raw HTML, remote images, executable links, citations or fabricated tool/source UI are added. Private reasoning is excluded upstream. PM owns visual, keyboard/IME, mobile-keyboard and UX acceptance; no browser/screenshot automation is used.

`client.test.tsx` verifies parser chunking, creation/scope, denied reads, draft preservation, history bounds/navigation, replay, same-ID retry, provisional/confirmed UI state, failure, EOF and abort/Stop orchestration entirely offline. The real-adapter tests additionally verify compatible GPT-OSS request options and separation of its default reasoning field.

## P3.3 explicit confirmation and uncertain-save recovery

The preview invokes `workspace/actions.confirmNoteProposal` only from **Save note**, never from ordinary chat text or the model's `prepareNote`. It sends the canonical edited `{proposalId,projectId,title,content,noteDate}`; general chat requires explicit owned-project selection, while project scope stays fixed. The backend verifies a fresh session and owns the full confirmation transaction (see the workspace README and proposal contract).

`ChatSession` synchronously records the exact submitted payload before awaiting an acknowledgement; duplicate clicks do not dispatch a second action. Saving/checking/uncertain/retry states freeze fields and participate in existing unsaved navigation/sign-out guards. Known definite input/authorization/conflict errors retain editable fields and safe messages. Success displays **Note saved** and the verified canonical **Open saved note** link, with no actionable Save button.

UNAVAILABLE, a thrown action or malformed acknowledgement is not proof of rollback. The client shows **Save unconfirmed** and invokes the existing authorized single-proposal read, never an automatic write. Confirmed reads recover the actual receipt. Proposed reads enable only explicit **Retry same save**, retaining the original canonical payload despite local/history reload; a failed read retains uncertainty and offers **Check saved status**. A rejected retry cannot discard the earlier unresolved operation. There is no manual-create fallback, new proposal/key or inference retry.

Confirmed receipts are monotonic within the view and cannot be replaced by an older proposed history/RSC/recovery response. History receipts on document reload recover server truth; local edits/pending-operation memory are not browser-persisted. Existing chat turn/replay/Stop/deadline behavior and the meaning of stream `finish.persisted` are unchanged.

Offline tests cover canonical edited input, explicit general-project selection, double clicks, safe errors, lost acknowledgement/read failure, frozen-payload retry, malformed/foreign-source receipts, late stale responses, reload and SSR saved-state controls. Real PostgreSQL concurrency/rollback, live Groq tools and authenticated browser/mobile checks remain deferred, not established by these tests.

The merged P3.4B fix (`6c24c1e`) marks the always-rendered composer with session-level unsaved state. Sign-out therefore warns even when an unresolved proposal is outside the current history page. Its regression test covers retained payload/dirty state and composer wiring; the fixture includes the metadata required by the history DTO.
